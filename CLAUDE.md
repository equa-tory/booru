# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
A self-hosted, single-user "booru"-style photo/video/PDF gallery built on Django 6 + SQLite, with an htmx-driven frontend. No cloud, one shared password (`GALLERY_PASSWORD`; set it in the untracked `booru/local_settings.py`, which overrides `booru/settings.py` — see `local_settings.py.example`. The repo is public, so never put real secrets in `settings.py`). Files on disk are the source of truth; the DB only stores paths + metadata and never moves/renames originals except via explicit "organize"/"merge" actions.

## Commands
- Dev server: `python manage.py runserver`
- Migrate / make migrations: `python manage.py migrate` / `python manage.py makemigrations`
- Fresh install / re-install: `./install.sh [--yes] [--no-service]` — venv, `pip install -r requirements.txt`, generates the untracked `booru/local_settings.py` (password, media + backup folders, SECRET_KEY), migrates, renders `booru.service` (template with `@APP_DIR@/@USER@/@PORT@`) into `/etc/systemd/system/` and restarts it (default port 3002). Idempotent.
- Production (Linux/systemd): `./start.sh` — uses `venv/bin/python3`, runs makemigrations+migrate, `sudo`-restarts the `booru` systemd unit, then runs gunicorn (4 gevent workers, port 3001, 900s timeout). Windows dev uses runserver.
- Dependencies: `pip install -r requirements.txt` (pinned; includes gunicorn/gevent/onnxruntime/onnx/PyMuPDF). No linter is configured.
- Tests: `python manage.py test` (single test: `python manage.py test gallery.tests.ScanTests.test_scan_prunes_deleted_files_and_empty_posts`). `gallery/tests.py` covers scan, task cancel/dismiss, tag recount, auth cookies and backup/restore; scan tests run against a temp `MEDIA_ROOT`, backup tests against a temp SQLite file, never the real data.
- Downloads watcher (optional sidecar): `python watch_downloads.py --downloads <dir> --inbox <media/inbox>` — auto-moves new downloads/zips into the inbox.

## Adding media
Paths like `media/inbox/` below are relative to `settings.MEDIA_ROOT`, which may point outside the repo (overridden in the untracked `booru/local_settings.py`; the `settings.py` default is `./media`).
Two paths, both funnel through `gallery/utils.py::scan_inbox`:
1. Drop files into `media/inbox/` (subfolders OK), then click "scan inbox" (POST `/api/scan-bg/`).
2. Browser upload (POST `/api/upload/`) writes into `media/inbox/` then ingests.
Convention: `media/inbox/_/<folder>/` = one multi-image Post; loose files in `media/inbox/` = one Post each. Optional per-month tidy folders `inbox/YYYY-MM/DD/`.

## Architecture
- Single Django app `gallery`; project package `booru`.
- Models (`gallery/models.py`): `Post` (a gallery item) has many `Photo` (individual files, incl. video/PDF, `is_video` flag, `phash` for dedupe). `Tag` (M2M to Post) has a `category` (general/character/artist/meta/ai) and a denormalized `count` kept current via `Tag.update_count()`. `Folder` is either manual (explicit M2M posts) or "smart" (stores a query string re-run through `_build_post_qs`), and nests into a tree via `parent` (self-FK, `on_delete=CASCADE`) — organizational; opening a folder shows only its own directly-assigned posts unless `include_subfolders` is set (the "⊞" toggle on a folder row), which folds in every descendant folder's posts too (`Folder.descendant_ids()`, applied in `_build_post_qs`). `Task` is a DB-backed row tracking background jobs so progress survives page reloads and is visible to every gunicorn worker.
- `Photo.rel_path`/`rel_thumb_path` are stored relative to `settings.MEDIA_ROOT` (so relocating the whole media folder only means updating `MEDIA_ROOT`); the `file_path`/`thumb_path` properties resolve them to absolute paths and transparently tolerate legacy absolute values from before this became relative. `rebase_photo_paths()` in `utils.py` (wired to the "rebase paths" button) bulk-converts any remaining absolute rows.
- Ingestion/thumbnailing lives in `gallery/utils.py`: `ingest_photo`, `create_post_from_files`, `make_thumb`/`make_video_thumb` (ffmpeg)/`make_pdf_thumb` (PyMuPDF→pdftoppm fallback), `compute_phash`/`phash_distance`. Thumbnails are keyed by md5 of the source path and written to `media/thumbs/`.
- Views (`gallery/views.py`) are the whole controller layer — page renders + a large JSON API (URLs in `gallery/urls.py`). Frontend is server-rendered templates (`templates/gallery/`) + `static/js/htmx.min.js`; there is no JS build step. Infinite scroll pulls JSON from `/api/posts/`.

## Search DSL (in `gallery/views.py`)
The gallery query is built by `_build_post_qs`; token parsing is `_parse_tag_tokens` + `_term_to_q`. Supported search-box syntax:
- `a b` = AND, `( a ~ b )` = OR group (braces and spaces are significant), `-tag` = NOT
- `tag~` = fuzzy (Levenshtein), `ta*1` = glob wildcard, `file:name` / `folder:name` = path substring
Reuse these helpers rather than writing new query logic. `random` sort uses a seeded deterministic shuffle (`_apply_seeded_order`) so gallery/scroll/prev-next stay consistent — the seed lives in the URL.

## Background tasks
Heavy operations (scan, merge, ai_tag, dupes) run via `_start_task(kind, fn)` which spawns a daemon thread and records progress in a `Task` row. Each thread MUST `connection.close()` when done (already handled in the runner). The frontend polls `/api/tasks/`. There are both synchronous (`scan`, `merge_posts`, `ai_tag_all`) and background (`scan_bg`, `merge_bg`, `ai_tag_all_bg`) variants of the big operations — the `_bg` ones are the ones wired to the UI.
Tasks are cancellable: the stop button sets `Task.cancel_requested` (`/api/tasks/<id>/cancel/`) and every work fn calls `check_cancel(task)` (`gallery/utils.py`, raises `TaskCancelled`) between units of work — new long loops must do the same, and must never be cancelled mid-post. Finished cards dismiss individually (`/api/tasks/<id>/dismiss/`); `running` rows with no progress for 30 min are swept to `error` (the thread died with its worker). Bulk code should batch tag counts (`add_tags_to_post(..., recount=False)` + one `recount_tags()`), not call `Tag.update_count()` per tag/file.

## AI tagging
`run_ai_tagger` runs the WD14 ONNX tagger (`SmilingWolf/wd-vit-tagger-v3`, lazily downloaded + cached in `_get_wd14_model`, CUDA→CPU providers). For videos/PDFs it tags the generated thumbnail instead of the original. Always go through `apply_ai_tags(post)` (views.py), which wraps `run_ai_tagger` → `{'general': [...], 'character': [...]}`: general/rating tags (>= `AI_GENERAL_THRESHOLD` 0.35, first 40 in model order — unchanged) land in category `ai`; characters (>= `AI_CHARACTER_THRESHOLD` 0.85, top 12 by confidence, kept OUTSIDE the 40 cap — they sit last in the model's tag order and used to be cut off) land in category `character` (an existing `ai`-category character tag is promoted; user-set categories are never touched). It sets `Post.ai_tagged` and `Post.char_tagged`; `ai_tagged=True, char_tagged=False` = tagged by the old tagger, i.e. the candidates for a future characters-only re-tag (not built yet). Thresholds can be overridden in `local_settings.py`. **Runtime** (`gallery/ai_runtime.py`): every ONNX model goes through `ai_runtime.get_model(key, path)` → `ManagedModel` (quacks like an `InferenceSession`): CUDA when `onnxruntime-gpu` + CUDA libs work, automatic CPU fallback if CUDA fails mid-run (cuDNN mismatch/OOM → CPU for 10 min, then retried), lazy load, and unload after `AI_IDLE_UNLOAD_SECONDS` (120) idle so the shared GPU's VRAM (ComfyUI uses it too) is released. Each gunicorn worker is its own process with its own sessions. GPU install: `./install.sh --gpu` (`requirements-gpu.txt`): `onnxruntime-gpu[cuda,cudnn]==1.26.0` — 1.26 is the last release whose default wheel is CUDA 12 (≥1.27 defaults to CUDA 13, which dropped Pascal) — plus `nvidia-cudnn-cu12==9.10.2.21`: cuDNN 9.27 fails on the Tesla P4 (`CUDNN_FE failure 11`), 9.5.1/9.10.2 work. Measured on the P4: WD ViT 84 ms/img vs 573 ms CPU, identical outputs. The P4 has no fast FP16/int8, so only FP32 models make sense. The default pip index on this machine is a Nexus mirror that returned no packages; pass `--index-url https://pypi.org/simple` if installs fail.
**Second character model** (`gallery/char_tagger.py`): PixAI tagger v0.9 (DeepGHS ONNX export, 1.27 GB, 3,720 characters, trained to Jan 2025, ~0.3 s/img on the P4). It only ever ADDS character tags (category `character`) and sets `Post.char_model='pixai'` (`''` = old/unchecked, `'wd14'` = fixed WD14 pass; WD14 never downgrades a `pixai` post). Entry points: `apply_character_model(post)`; per-post button (`/api/post/<id>/tag-characters/`); settings → AI tagging → "re-tag characters for N posts" (`/api/ai/char-retag/`, exclusive + cancellable + resumable Task `char_retag`, newest first, skips `char_model='pixai'`, downloads the model first if missing); optional `aiCharAuto` pref runs it after every WD14 tagging. Its preprocessing differs from WD14: squash-resize to 448, RGB, mean=std=0.5, NCHW (see `_preprocess`). The model downloads with the Xet transfer disabled (`HF_HUB_DISABLE_XET`) because the default path stalls here.
- Separately, `sync_sound_tag`/`has_audio_stream` (ffprobe-based, in `gallery/utils.py`) add/remove a `sound` tag on video posts; driven per-post during ingest and in bulk via the `sound_tag_all_bg` background task.

## Middleware & caching (`gallery/middleware.py`)
- Auth uses unique names (`booru_sessionid`, `booru_csrftoken`, session key `booru_authed`) because other local Django apps share the default cookie names across ports and logged each other out — don't revert to the defaults.
- `LoginRequiredMiddleware`: session password gate; `sw.js` and `/login|/logout` are exempt.
- `CacheHeadersMiddleware`: `/static/` cached a year (immutable), `/media/` a day; thumbnails cache-bust via a `?v=<mtime>` param added in `Photo.thumb_url`.

## Database backups (`gallery/backup.py`)
Only `db.sqlite3` is backed up (media files are never touched), via sqlite's online-backup API in one step (consistent under WAL, no stray `-wal/-shm`). Settings (enabled, max backups, interval hours, folder) live under the `backup` key of the server-side prefs (DB, see "Server-side settings" — so every backup also contains ALL settings: quick links, main AI model, key bindings…; a restore re-applies the CURRENT backup config afterwards); the default folder is `settings.BACKUP_DIR`. UI: the "⚙ settings" modal (`templates/gallery/_settings_modal.html`), which also hosts the maintenance buttons (tag sound, keys, re-tidy all, rebase paths). A scheduler thread started from `GalleryConfig.ready()` (gunicorn/runserver only) checks every 10 min; a flock'd lock file in the backup folder keeps the 4 workers from duplicating a run. Rotation only deletes `booru-*.sqlite3`. Restore (from the folder listing or an upload) validates the file, saves `pre-restore.sqlite3`, overwrites the live DB in place, carries `django_session` rows across, runs `migrate`, and re-creates its own Task row (the restored DB doesn't contain it).

## Sidebar tags (`index` view, `_sidebar_tags`)
The desktop sidebar shows `SIDEBAR_TAG_CAP` (150; 40 in fast mode) tags chosen per page load: pinned favorites first, then an EQUAL share per tag type (`_fair_shares`: unused slots flow to the bigger types), picked at random inside each type weighted by sqrt(usage) (raw counts repeated half the list between reloads), grouped by type with headings. This replaced "top N ordered by category rank", where ~850 character tags starved every other type. Only full page loads re-sample (the htmx grid response has no sidebar). The mobile tag sheet (`tags_all`) still lists everything.

## AI models, selector, "my model"
- `gallery/ai_models.py`: registry for `wd14` (default), `pixai`, `custom` (my model): `status/is_ready/download/delete`; HF models live in the HF cache, "my model" in `settings.AI_MODELS_DIR` (default `./ai_models`, untracked). Downloads run as Tasks with Xet disabled. Settings → "AI models" has download/delete per model, the **main tagger selector** (pref `aiMainModel`, resolved by `_main_model()`, falls back to wd14 if the chosen model is missing; PixAI as main = no rating tags, different vocabulary) and **Free VRAM**.
- **Free VRAM** (`ai_runtime.request_unload_all`): writes `AI_MODELS_DIR/.unload`; every worker's reaper polls it (3 s) and force-unloads all models even mid-run, keeps freeing for 60 s, and the endpoint cancels running AI tasks (`AI_TASK_KINDS`). A CUDA context (~120 MiB/worker) can only be released by restarting workers ("restart workers too" = graceful SIGHUP to the gunicorn master).
- **My model** (`gallery/custom_model.py`): a clone of the default ONNX with one extra graph output (the 768-d pooled feature tensor feeding the classifier `Gemm`, found structurally; `clone_default` refuses any clone whose default outputs are not bit-identical). Taught knowledge = linear heads on those features (`heads.npz`), trained by a numpy-only L2 logistic regression with 5-fold CV; the threshold is picked on out-of-fold scores with precision re-estimated for a rare concept (prior `CUSTOM_PREVALENCE_PRIOR`). DB: `CustomConcept`, `CustomExample` (label ±1, cached features), `PostFeature` (library index), `CustomApplied` (undoable bulk tagging). Flow: select posts → "🎓 teach AI" (`/api/custom/examples/`; "don't" also removes the tag) → train (Task `custom_train`; auto-samples 4× negatives from the library) → optionally "index library" (Task `custom_scan`, ~0.4 s/post, resumable) → preview / review-uncertain (opens `/?ids=…`) → apply / undo. With main=custom, `run_ai_tagger` returns the exact default tags plus `res['learned']`, stored via `custom_model.apply_learned`. Concept names may not collide with a default-model tag. Cached features are tied to the clone's source hash (`model_hash`).
- Tests use the test DB for prefs; the module-level patch of `prefs.legacy_path` in `gallery/tests.py` stops them importing/renaming the real legacy `prefs.json` — keep it, and never write test cleanups that delete files outside a temp dir.

## Search box, tag buttons, quick links
- Suggestions: `searchTokenAt`/`applySuggestion`/`fetchTagSug` (inline in `base.html` between `// <searchtok>` markers, unit-tested in Node) are the ONLY token logic for the three search inputs (sidebar, post page, phone sheet): the token under the caret (a leading `-` is kept, `( ) ~ file: folder: * ~ >` get none, a caret after a space has none), other tokens are excluded, stale responses are dropped. `/api/tag-search/` ranks prefix matches first, hides count-0 tags.
- Every tag row has `+` (add) and `−` (add `-tag`, i.e. exclude); `addTagToSearch(name, neg)` swaps the opposite one if present (sidebar `index.html`, post chips `detail.html` markup AND `renderTags`, phone sheet).
- "remember sort" (`.remember-sort-btn`, localStorage) exists in the desktop sidebar and the phone sheet; one toggle drives all.
- Quick links: settings → "quick links" (`/api/quick-links/`, pref `quickLinks`, max 20, http(s) or `/path` only, parsed by `parse_quick_links`); rendered in the header by the `gallery.context.quick_links` context processor.
- Post page: on open the first content element is focused (video, else the scroll/paged container) so native keys work; with a focused video only Space/arrows/k/j/l/f/m/Home/End stay native. "fit item to screen" also works for multi-image posts in scroll mode (`applyFitMulti`: one size from the first item, applied once on open/toggle/resize, never per item). With fit on, the size slider is a multiplier on the fit (`fitFactor()`: desktop px/1200, phone %/100, capped at 1) for single and multi posts.
- Double-tap zoom (paged `attachZoom` and scroll `attachScrollZoom`) uses `makeDoubleTap()`: only a real tap (one finger, <12 px, <300 ms) can be half of a double-tap, otherwise a scroll started right after zooming in zoomed back out.
- The AI tag result carries `model` (`wd14`/`pixai`/`custom`) and `learned`; My model = default tags + only taught tags, so it can look identical to the default on posts without them (the toast and settings panel say which tagger ran).

## Multi-image tagging, media Range, back-to-post
- `apply_ai_tags(post)` with no `cover` tags up to `AI_MAX_IMAGES_PER_POST` (24, evenly spaced incl. first/last; one post has 6,000+ images) items of a multi-image post and `_merge_ai_results` sums them (tags ranked by how many items carry them, general cap 80, characters cap 20, only the strictest rating kept). A single image goes through unchanged. `Post.ai_multi` marks "all items tagged"; settings → AI tagging → "re-tag all multi-image posts" (`/api/ai/multi-retag/`, Task `ai_multi`, exclusive/cancellable/resumable, adds tags only). An explicit `cover` argument still tags just that image.
- `/media/` is served by `views.media_serve` (not Django's `static()`): HTTP Range (206/416, `Accept-Ranges`, `If-Range`) — Chromium cannot seek or stream videos without it. Plain GETs use `FileResponse`.
- Leaving a post for the gallery (`goBack`, `swipeDownExit`, `goToGalleryPage`, `goToLibraryPage` in `detail.html`) stores `sessionStorage.focusPost`; `index.html::restoreFocusPost` scrolls that card to the centre (loading infinite-scroll pages until found) and flashes it; the old pixel-based `scrollY`/`infScroll` restore is only the fallback.

- `Photo.media_url`/`thumb_url` are percent-encoded via `Photo._url_for` (a `#`/`?`/`%` in a file name used to cut the URL → 404 → empty post) and are `''` for paths outside `MEDIA_ROOT`. A thumbnail whose file is gone (stored path from before the media folder moved) is rebuilt by the "rebase paths" task (`_repair_missing_thumbs`). Detail pages retry a failed `/media/` image once, then show "failed to load: <name>".
- Sidebar tag filter: only `#tag-list .tag-entry` rows have `data-name`; the folder tree rows reuse the class `tag-entry` — never query `.tag-entry` globally (it threw before the suggestion request, so suggestions never appeared).
- Settings live in the UNTRACKED `booru/local_settings.py` (MEDIA_ROOT, GALLERY_PASSWORD, BACKUP_DIR, SECRET_KEY), imported by the last lines of `booru/settings.py` — that is why they are not visible in `settings.py`.

- Unprocessed posts: `?proc=none|noai|nopixai` filters the gallery to posts the AI never touched (settings → debug overlays has the buttons with counts; `proc` rides along in nav/search params and shows as a pill).

## AI edit (ComfyUI img2img + Ollama prompt) — `gallery/comfy.py`
- Scroll-mode posts show a small round "✎" button on every still image (not video/PDF/GIF): hover on desktop, one tap on a phone (`toggleEditBtn`, 5 s). There is NO button in paged mode (the user never uses it). The box (`#aiedit-backdrop` in `detail.html`) has the request, an Ollama model select (remembered in pref `comfy.ollama_model`), seed, denoise slider and "preview prompt" (editable prompt; sending `positive` skips the LLM).
- Flow (`views.comfy_edit`, Task `comfy_edit`, exclusive, in `AI_TASK_KINDS`): tag THAT item (`_edit_current_tags`) → `comfy.to_prompt` (Ollama `/api/chat`, JSON schema, `think:false`, model kept 2 min). The model returns only a DIFF `{add, remove, denoise, note}` (few-shot system prompt); `apply_diff` + `prompt_texts` build the prompt: added tags first with weight `ADD_WEIGHT` 1.3, removed tags dropped from the positive and put in the negative. Asking for the whole new list made small models echo the old picture (#37111: "astronaut suit" lost among 40 school-uniform tags, removals only in the negative). No tool calling: the schema-enforced `format` works with any Ollama model; a "no change" answer falls back to the request text, weighted → `comfy.generate` (upload to ComfyUI input/booru, `build_img2img`, `/prompt`, poll `/history`, download via `/view`, `check_cancel` → `/interrupt`) → file in `MEDIA_ROOT/ai_edits/YYYY-MM/` → NEW post (`source_post`, `source_photo`, `gen_info`, meta tag `ai_edit`) → ComfyUI `/free` → `apply_ai_tags`. A generated post has "⤴ original #N" in the top bar (and the phone mini bar) plus "made from #N (item k)", the source lists "AI edits", "edit again" reopens the box with the request.
- The workflow is built in code (`build_img2img`); the same JSON ships as `docs/comfyui/booru_img2img_api.json` (a test keeps it in sync; drag it into ComfyUI). Output node is `PreviewImage` (ComfyUI's output folder is a network share). Settings = pref `comfy` (settings → "AI edit (ComfyUI)"): URLs, model, checkpoint (WAI-Illustrious v1.5 fp8), steps 20, cfg 5.5, euler_ancestral/normal, denoise 0.6, 0.8 MP, optional GPU-temperature gate (`WaitForGPUTemperature` custom node), quality prefix, default negative.
- Lessons: the user's own workflow "only copied the vibe" because KSampler denoise was 1.0 (= txt2img); real edits need 0.45-0.8 (colour 0.6, outfit 0.75; slider max 0.9). The Tesla P4 needs ~9 s/step at 1 MP (28 steps = 4 min), hence 20 steps / 0.8 MP (~2.5 min). Ollama here runs on the CPU (`/api/ps` size_vram 0): ~35-55 s per prompt, no VRAM conflict — `comfy.unload_ollama` only unloads a model that actually sits in VRAM. Tags are escaped (`escape_tag`: `_`→space, `(`→`\(`). Always `httpx` with `trust_env=False` (HTTP(S)_PROXY is set on this machine). Free VRAM also calls ComfyUI `/free`.
- Phase 2 ideas (not built): LoRA picker (the builder already takes `loras=[(name, strength)]`), inpaint mask, ControlNet.

## Settings panel debug overlays
"⚙ settings" → debug overlays toggles badges on every grid card (AI ✓/✗, characters-checked `wd ✓`/`px ✓`/✗, folder name/none, post id). They are CSS-only: each card always carries a `.dbg` block (server template `_photo_grid.html` AND the JS `makeCard` in `index.html` — keep both in sync) and body classes `dbg-ai/ch/folder/id` (localStorage `dbgOverlay`, applied by `applyDbg()` in `base.html`) reveal them. `posts_json` supplies `ai`, `chars`, `char_model`, `folders`; the grid query prefetches `folders` for this — keep it.

## Thumbnails
`_regen_photo_thumb(photo, pct)` (views.py) is the single implementation behind the per-photo regen button and the bulk "pic thumbs" action (`/api/bulk-regen-thumb/`, covers that are pictures/gif/pdf); videos in a bulk selection go through `bulk_video_thumb` (needs the frame %).

## Duplicate detection
`duplicates` view groups posts by cover-image perceptual hash (`phash_distance`); videos only compare with videos (tighter threshold), GIF vs still is avoided, and `Post.not_dupes` (symmetrical M2M) pairs are skipped.

## Gotchas
- `README.md` is stale (describes no-login, CLIP/transformers tagging, swapping `run_ai_tagger`); trust this file and the code instead.
- Server-side settings: `gallery/prefs.py` (`get/set/all/update`, `Setting` rows holding JSON; `/api/prefs/`, `/api/pref/set/`). They used to live in a shared `prefs.json` that every worker rewrote whole (and `recent_add` did so non-atomically on each post view), which silently wiped keys written in between (quick links, main AI model, char-model toggle). Never write settings any other way; use `prefs.update(key, fn)` for read-modify-write. The old file is imported once and renamed `prefs.json.imported`. Test DB is file-backed (`TEST NAME` in `settings.py`) so thread-concurrency tests are realistic.
- `booru-main/` in the repo root is an untracked stray copy of the project; ignore it and don't edit files there.
- SQLite is tuned for concurrency in `settings.py` (WAL, `busy_timeout`, `transaction_mode=IMMEDIATE`) because gunicorn gevent workers otherwise serialize on the write lock.
- Gallery grid relies on `prefetch_related('tags','images')`; `Post.cover`/`image_count`/`has_video` read the prefetched cache to avoid N+1 queries — preserve the prefetch when touching those code paths.
- The network path shown on a post (copy / open in explorer) is `_net_prefix()`: the `netPathPrefix` pref (settings → network path) or an automatic guess `\\<host from the address bar, else LAN IP>\<share>\...` from `MEDIA_ROOT` (`/mnt/<share>/…`). The duplicates page uses the same builder (no request → LAN IP).
- `views.py` contains commented-out dead blocks and a legacy WD14-swap note; ignore them.
